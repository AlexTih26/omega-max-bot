# Краткий контекст

Репозиторий `/MAX_BOT` (`omega-max-bot`) объединяет MAX-бота, web/PWA-контуры,
старую Таксимо, новую Таксимо и РУМЕКС. Эта память — быстрый ориентир для
задач. Развёрнутое и актуализируемое описание — в корневом `README.md`, целевая
модель — в `taksimo-unified-model.md` (она **переопределяет** всё, что ниже,
если есть расхождение).

Сведения ниже подтверждены исходным кодом и шаблонами конфигурации репозитория.
Они **не подтверждают** фактическое состояние production-сервера, Nginx,
systemd/cron, сертификатов, рабочих БД, резервных копий или развёрнутой ревизии.
Не читать секреты, `.env`, рабочие базы и журналы без отдельного явного запроса.

## Главное: модель меняется

С 12.10.2026 согласована **новая целевая модель**: одна программа на MySQL,
документы и физика в одной БД, мост `rumex_taksimo_bridge.py` и изоляция
контуров **уходят**. Всё, что ниже описывает «изоляцию РУМЕКС ↔ новая Таксимо»,
— это **текущее состояние до переключения**, а не цель. Подробно:
`taksimo-unified-model.md` и Часть I `README.md`.

Старая Таксимо (`data/taksimo.db`) **не трогается никогда** — она источник
правил, сетки, тупиков и опыта, пока новая её не заменит.

## Архитектура и контуры (текущее состояние)

```text
Браузер / MAX mini-app
    -> Nginx (HTTPS, web/)
    -> общий aiohttp на 127.0.0.1:8765
    -> bot.py / MAX long polling

Контуры: OMEGA/MAX | legacy Таксимо | новая Таксимо | РУМЕКС | Кодар
```

- `fotonych-bot/bot.py` запускает MAX long polling и общий HTTP-сервер.
- `fotonych-bot/comments_api.py` — историческое имя сборщика маршрутов общего
  `aiohttp` API, а не только API комментариев.
- Шаблоны Nginx: `scripts/nginx-avtmsk.ru.conf` и
  `scripts/nginx-max.avtmsk.ru.conf`.
- Legacy Таксимо владеет SQLite `data/taksimo.db`; новая Таксимо владеет
  MySQL `taksimo_new`; РУМЕКС владеет SQLite-реестром `data/rumex_registry.db`.

## Границы разработки

1. **Не менять legacy Таксимо и не писать в `/MAX_BOT/data/taksimo.db`.**
2. Новая Таксимо может получать legacy-проекции только через
   `taksimo_legacy_reader.py`: короткие SQLite-подключения `mode=ro`, таймаут
   2 секунды, одно read-only чтение без частичного снимка.
3. **До переключения** новая Таксимо и РУМЕКС не читают и не записывают базы
   друг друга напрямую; все бизнес-факты проходят только через
   `rumex_taksimo_bridge.py` и его служебный HTTP-контракт. **После
   переключения** это правило снимается — база становится одна.
4. **До переключения** не смешивать авторизацию legacy Таксимо, новой Таксимо,
   бухгалтеров РУМЕКС, диспетчера и управления РУМЕКС. **Цель** — одна
   авторизация с входами по ролям и детальным журналом действий.
5. Подтверждённую историю не переписывать: исправления выполняются новым
   событием или отменой операции.
6. Не коммитить `.env`, токены, PIN, базы, WAL/SHM, логи и runtime-файлы.
   Использовать только явный `git add <пути>`.
7. Не применять миграции, не перезапускать сервисы и не выполнять deployment
   без отдельного разрешения.

## РУМЕКС ↔ новая Таксимо (текущий поток, до переключения)

- Бизнес-цепочка: РУМЕКС (диспетчер, бухгалтер, ЭР/ТТН) -> автомобиль -> новая
  Таксимо (ожидаемая поставка, физическая приёмка, склад, вагон) -> Кодар.
- `rumex_taksimo_bridge.py` использует локальный HTTP API, Bearer-токен и
  `Idempotency-Key`.
- РУМЕКС передаёт ожидаемые поставки и копии ТТН в новую Таксимо.
- Новая Таксимо кладёт физические факты в outbox; мост сначала фиксирует их в
  РУМЕКС, затем подтверждает запись outbox.
- **Расхождение с целевой моделью:** тестовый рейс уходит в новую Таксимо
  **до** проверки бухгалтером; по цели — **после** проверки и печати ТТН.
- **Расхождение с целевой моделью:** автоодобрение тестовой погрузки через
  10 минут подменяет ручную утреннюю проверку бухгалтера (Москва).
- **Расхождение с целевой моделью:** обратные физические факты тестового
  реестра могут отклоняться (приёмник проверяет боевые снимки, а не тестовые).

Основные файлы: `rumex_taksimo_bridge.py`, `rumex_registry_*.py`,
`taksimo_new_api.py`, `taksimo_new_store.py`.

## Новая Таксимо (текущее состояние)

- Код: `fotonych-bot/taksimo_new_*.py`; PWA: `web/taksimo-new/`.
- Отдельные MySQL-схема, PIN-сессии операторов, журнал событий, outbox,
  уведомления и отчёты.
- Роли операторов: `operator1`, `operator2`, `operator3`.
- Жизненный цикл вагона:

  ```text
  forming -> loaded -> in_transit -> at_kodar -> unloaded_bts_east
          -> returned_empty -> forming
  ```

- Собственные позиции вагонов (30 мест): `gruzovoy_1` (Грузовой 1, 1–10),
  `gruzovoy_2` (Грузовой 2 / Туран, 1–10), `gruzovoy_3` (Грузовой 3, 1–10).
- **Расхождение с целевой моделью:** эти позиции **не сопоставляются** со
  слотами старой Таксимо. По цели сетка `13×25` и тупики старой
  **наследуются**, плюс третий тупик; схема вагона становится сущностью.

## Legacy Таксимо: live и архив

- Путь SQLite: `/MAX_BOT/data/taksimo.db`.
- Разрешённые read-only проекции: машины, вагоны, места вагонов, плиты, плиты
  склада, сессии, отправленные плиты, история вагонов.
- Переменная даты перехода:
  `TAKSIMO_LEGACY_CUTOVER_AT` в ISO 8601 с часовым поясом.

| Условие | Режим |
| --- | --- |
| Дата X не задана или ещё не наступила | `live`: согласованное `mode=ro` чтение SQLite |
| После X и архив уже есть | неизменяемый архив MySQL |
| После X без архива | первый успешный запрос создаёт JSON-снимок MySQL |
| SQLite недоступна после X | `snapshot_pending`, пустой снимок не создаётся |
| Формат даты неверен | `configuration_error`, SQLite не читается |

Ключевое ограничение: снимок появляется при первом успешном запросе после X, а
не в точный момент X.

**Даты по новой модели:** `11.10.2026` — дата импорта данных и старта отчётов
новой программы. **Дата X (день переключения)** — отдельно, выбирается по
готовности модулей; в этот день переносится состояние (блоки, вагоны, машины).

## Доменные правила (наследуются от старой Таксимо)

- буквы плит: `A–F`, `K`; суффиксы: `""`, `к`, `а`, `тк`, `скол`;
- рабочие зоны: `ХРАНЕНИЯ`, `ГРУЗОВОЙ`, `ТУРАН`, третий тупик;
- системные зоны: `В КОДАР`, `БТС ВОСТОК`;
- сетка склада: `13 × 25`; макс. 4 плиты в ячейке;
- макс. плит в вагоне: **9 / 8 / 16 — по схеме вагона** (в старой — 9);
- **три** тупика по 10 мест: `ГРУЗОВОЙ`, `ТУРАН`, третий.

## Веса блоков

```text
A=7780  B=7900  C=8080  D=8080  E=7900  F=7780  K=3850 кг
```

Справочник по буквам, общий. **Подтверждены владельцем 12.10.2026** — пометка
«предварительные» устарела. В истории рейса и строках документов сохраняется
снимок веса и стоимости: изменение справочника не переписывает прошлое.

## Авторизация (текущее состояние)

| Контур | Вход |
| --- | --- |
| Legacy Таксимо | PIN из `TAKSIMO_USERS`, подписанный cookie `taksimo_auth` |
| Новая Таксимо | PIN операторов, серверная сессия `taksimo_new_auth` |
| РУМЕКС-бухгалтеры | PIN, `Бухгалтер 1`, `Бухгалтер 2`, `Бухгалтер 3`; сессия `rumex_accountant_auth` |
| РУМЕКС-тестовый диспетчер | пароль, сессия `rumex_test_dispatcher_auth` |
| Управление РУМЕКС | MAX или пароль, сессия `rumex_management_auth` |

**Цель:** одна авторизация, входы по ролям, детальный журнал действий.

Секреты не хранятся в Git. Закрытые настройки MySQL новой Таксимо ожидаются в
`/root/.config/taksimo-new/`; содержимое этих файлов не читать без разрешения.

## Вечерний отчёт о погрузке

Источник — **legacy Таксимо**, время **16:00 МСК** из `.env`. Запускается
legacy-цикл (`bot.py:596`). Подробно и с результатами проверки —
`taksimo-evening-report.md`.

## Миграции, бэкапы, проверка

- Миграции MySQL: `migrations/taksimo_new/`, запуск только через
  `scripts/migrate-taksimo-new-mysql.sh` технической учётной записью.
- `009_legacy_archive_and_wagon_positions.sql` добавляет архив legacy и 30
  позиций вагонов; миграция не применяется автоматически, не тестировалась на
  production и не должна применяться без проверки целевой MySQL-копии.
- Бэкапы: `backup-taksimo-db.sh`, `backup-rumex-registry-db.sh`,
  `backup-taksimo-new-mysql.sh`, `backup-env.sh`.
- Watchdog проверяет legacy API и перезапускает `bot.py`; он не покрывает
  здоровье MySQL новой Таксимо и моста РУМЕКС.
- Целевая локальная проверка legacy/новой границы: 24 теста прошли; 6 HTTP-тестов
  пропущены без `aiohttp`. Production-миграции и серверный аудит не выполнялись.

## Открытые вопросы

1. Выбрать дату X — день переключения с переносом состояния.
2. Согласовать способ обкатки: как данные вводятся параллельно в старую и новую.
3. Решить судьбу моста и таблиц РУМЕКС после переключения.
4. Пересмотреть автоодобрение тестовой погрузки через 10 минут.
5. Согласовать разбивку роли «оператор» по сменам/постам.
6. Решить, нужен ли отдельный журнал по водителям/перевозчикам.
7. Проверить миграцию `009` на целевой версии MySQL.
8. Подтвердить legacy SQLite-схему и read-only чтение на рабочей копии.
9. Добавить наблюдаемость новой MySQL и моста, удалённые бэкапы и проверку
   восстановления.
10. Выбрать облако для фото (S3: Яндекс или Сбер) по цене.
11. При необходимости провести отдельный read-only аудит реального сервера.

## Как использовать эту память

Перед задачами по этому проекту сначала прочитать `README.md`, этот файл,
`taksimo-unified-model.md` и файлы нужного контура. Перед изменением общего
контракта найти все его использования. Для кода новой Таксимо дополнительно
читать соответствующую миграцию и целевые тесты в `tests/`.
