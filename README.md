# OMEGA / MAX / РУМЕКС / Таксимо

Технический контекст репозитория `omega-max-bot`. Здесь собрана текущая
архитектура кода, границы контуров и правила их развития.

> **Важно.** Это описание сделано по исходному коду и конфигурационным
> шаблонам репозитория. Оно не подтверждает фактическое состояние сервера,
> Nginx, systemd/cron, сертификатов, баз данных, резервных копий или
> развёрнутой ревизии. В рамках подготовки документа не выполнялись SSH-аудит,
> просмотр секретов, рабочих БД, журналов и production-конфигурации.

## Состав платформы

Проект вырос из MAX-бота с комментариями к постам и теперь содержит несколько
изолированных рабочих контуров:

| Контур | Назначение | Владелец данных |
| --- | --- | --- |
| OMEGA / MAX | long polling MAX, AI-помощник, комментарии, служебные чаты и уведомления | собственные SQLite/файловые данные соответствующего модуля |
| Legacy Таксимо | действующий исторический контур площадки и его SQLite-база | старая Таксимо; новый код её не изменяет |
| Новая Таксимо | отдельная PWA приёмки, склада, вагонов и отчётов | изолированная MySQL БД `taksimo_new` |
| РУМЕКС | диспетчерский и бухгалтерский учёт автодоставки, ЭР и ТТН | реестр РУМЕКС |
| Кодар | целевая часть логистической цепочки: прибытие, выгрузка и возврат вагона | фиксируется в бизнес-событиях нового контура/РУМЕКС |

Один процесс `fotonych-bot/bot.py` запускает MAX long polling и общий `aiohttp`
сервер. Историческое имя модуля `comments_api.py` не означает, что он обслуживает
только комментарии: он собирает маршруты общих HTTP-контуров на
`127.0.0.1:8765`.

```text
Браузер / MAX mini-app
          |
          v
   Nginx (HTTPS, статика web/)
          |
          v
  aiohttp 127.0.0.1:8765  <---->  bot.py / MAX long polling
          |
          +-- комментарии, FOTON, legacy Таксимо, РУМЕКС
          +-- новая Таксимо (MySQL)
          +-- серверный мост РУМЕКС <-> новая Таксимо
```

В репозитории есть шаблоны Nginx для `avtmsk.ru` и `max.avtmsk.ru`:

- `scripts/nginx-avtmsk.ru.conf` — статика из `/MAX_BOT/web`, API через
  `127.0.0.1:8765` и auth-request старой Таксимо;
- `scripts/nginx-max.avtmsk.ru.conf` — статика и API MAX-контуров через тот же
  локальный HTTP-сервер.

Наличие этих файлов **не означает**, что именно они установлены или активны на
сервере.

## Сквозной бизнес-процесс

Цепочка груза разделяет ответственность, а не объединяет все действия в один
кабинет:

```text
РУМЕКС: производство / диспетчер / бухгалтер / ТТН
    -> автомобильная доставка
    -> новая Таксимо: ожидаемая поставка, фактическая приёмка, склад
    -> вагон: позиция, загрузка, отправка
    -> Кодар: прибытие, выгрузка, возврат
```

1. Диспетчер РУМЕКС создаёт и ведёт автомобильный рейс.
2. Бухгалтер РУМЕКС проверяет сведения и выпускает ЭР/ТТН.
3. Серверный мост передаёт в новую Таксимо ожидаемую поставку и копии ТТН.
4. Оператор новой Таксимо принимает физические блоки и размещает их на складе
   или в вагоне.
5. Факты загрузки и жизненного цикла вагона записываются в outbox новой
   Таксимо, после чего мост фиксирует их в РУМЕКС и подтверждает доставку.

Стартовые номинальные веса типов блоков заданы в РУМЕКС: `A=7780`, `B=7900`,
`C=8080`, `D=8080`, `E=7900`, `F=7780`, `K=3850` кг. В коде они прямо помечены
как предварительные до подтверждения ответственным сотрудником; это не следует
считать окончательным производственным нормативом.

Полное бизнес-описание цепочки находится в
[`docs/rumex-taksimo-kodar-ecosystem.md`](docs/rumex-taksimo-kodar-ecosystem.md).

## Границы интеграции РУМЕКС и новой Таксимо

`fotonych-bot/rumex_taksimo_bridge.py` — единственная серверная граница обмена
бизнес-фактами между РУМЕКС и новой Таксимо.

- Мост обращается к локальному HTTP API (по умолчанию
  `http://127.0.0.1:8765`) с Bearer-токеном и `Idempotency-Key`.
- РУМЕКС отправляет ожидаемые поставки и документы в интеграционные точки новой
  Таксимо.
- Из новой Таксимо мост читает outbox физических фактов, сначала записывает
  каждый факт в РУМЕКС, затем подтверждает его в outbox.
- Новой Таксимо и РУМЕКС запрещены прямые межбазовые чтения и записи; мост не
  работает со старой Таксимо.

Такой порядок делает повторную доставку безопасной и не превращает ошибку сети
в потерю подтверждённого складского факта.

## Новая Таксимо

Новый контур расположен в `fotonych-bot/taksimo_new_*.py` и статике
`web/taksimo-new/`. Он имеет отдельные MySQL-схему, операторские PIN-сессии,
PWA-интерфейс, журнал событий, outbox, уведомления и отчёты.

### Вагонный цикл и позиции

Рабочий цикл вагона в доменной модели:

```text
forming -> loaded -> in_transit -> at_kodar -> unloaded_bts_east
        -> returned_empty -> forming
```

Для новых вагонов предусмотрены только собственные позиции нового контура:

| Код | Отображение | Места |
| --- | --- | --- |
| `gruzovoy_1` | Грузовой 1 | 1–10 |
| `gruzovoy_2` | Грузовой 2 (Туран) | 1–10 |
| `gruzovoy_3` | Грузовой 3 | 1–10 |

Итого 30 мест. Позиция обязательна при прямом размещении блока в вагон, прямой
вагонной загрузке, переводе вагона в `loaded` и возврате порожнего вагона.
История назначения и освобождения позиции записывается отдельно. Позиции старой
Таксимо намеренно не переносятся и не сопоставляются с новыми.

### Учётные границы

Авторизация каждого контура независима:

| Контур | Учётные роли/вход |
| --- | --- |
| Старая Таксимо | существующий legacy-вход и его Nginx auth-request |
| Новая Таксимо | PIN-сессии `operator1`, `operator2`, `operator3` |
| РУМЕКС: бухгалтеры | `Бухгалтер 1`, `Бухгалтер 2`, `Бухгалтер 3`; справочниками реестра управляет только Бухгалтер 1 |
| РУМЕКС: диспетчер | отдельный кабинет и отдельные сессии |
| РУМЕКС: управление | отдельный административный контур |

Данные входа, PIN, токены и пароль MySQL не должны попадать в репозиторий.
Шаблон `fotonych-bot/.env.example` описывает только имена переменных. Частные
настройки новой Таксимо предполагаются в закрытых файлах `/root/.config/taksimo-new/`:
отдельно для приложения, мигратора и резервного копирования.

## Совместимость со старой Таксимо

Старая SQLite-база находится по пути, заданному в
`taksimo_legacy_reader.py` (`/MAX_BOT/data/taksimo.db`). Новый код никогда не
пишет в неё.

До согласованной даты X новая PWA может читать только разрешённые legacy-проекции
через короткоживущее SQLite-подключение с URI `mode=ro`, таймаутом 2 секунды и
одной read-транзакцией. Разрешены проекции машин, вагонов, вагонных мест, плит,
плит склада, сессий, отправленных плит и истории вагонов. Ошибка полного чтения
не должна выдавать частичный снимок.

Необязательная переменная `TAKSIMO_LEGACY_CUTOVER_AT` задаётся только в ISO 8601
с часовым поясом.

| Условие | Поведение |
| --- | --- |
| Дата X не задана | доступен только live read-only просмотр SQLite |
| До даты X | `mode=live`, создаётся согласованный read-only снимок для ответа |
| После даты X и архив есть | отдаётся неизменяемый MySQL-архив |
| После даты X, архива нет | первый **успешный запрос** создаёт единый JSON-снимок в MySQL |
| SQLite недоступна после X | `mode=snapshot_pending`; пустой архив не создаётся |
| Формат даты неверен | `mode=configuration_error`; чтение SQLite не выполняется |

Критичное ограничение: снимок создаётся при первом успешном запросе после X, а не
по планировщику ровно в момент X. Для требований аудита или строго определённого
времени перехода это нужно отдельно согласовать и реализовать как операционную
процедуру. Дата X сейчас не зафиксирована этим репозиторием.

## Миграции новой Таксимо

Миграции MySQL хранятся в `migrations/taksimo_new/` и запускаются только
технической учётной записью через `scripts/migrate-taksimo-new-mysql.sh`.
Приложение не выполняет миграции само.

| Группа | Содержание |
| --- | --- |
| `001` | начальная схема нового изолированного контура |
| `002` | проверки целостности и триггеры |
| `003–004` | отмены операций и их триггеры |
| `005–006` | outbox-мост РУМЕКС и физический жизненный цикл, включая триггеры |
| `007` | возврат порожнего вагона и триггеры |
| `008` | документы приёмки/копии ТТН |
| `009` | архив legacy-снимка и независимые позиции вагонов 3 x 10 |

`009_legacy_archive_and_wagon_positions.sql` не открывает и не изменяет SQLite.
Он ещё не подтверждён запуском на production и должен быть проверен на
одноразовой MySQL-копии, совместимой с целевой версией MySQL, до применения.

## Резервное копирование и контроль

В репозитории есть следующие скрипты:

- `scripts/backup-taksimo-db.sh` — резервное копирование legacy SQLite;
- `scripts/backup-rumex-registry-db.sh` — резервное копирование реестра РУМЕКС;
- `scripts/backup-taksimo-new-mysql.sh` — `mysqldump --single-transaction` новой
  MySQL БД, проверка `gzip`, SHA-256 и локальная ротация (по умолчанию 31 день);
- `scripts/backup-env.sh` — резервное копирование окружения;
- `scripts/taksimo-watchdog.sh` и `scripts/cron-taksimo-watchdog.txt` — проверка
  legacy API и перезапуск `bot.py` с cooldown.

Эти скрипты описывают предусмотренный механизм, но не подтверждают наличие
расписания, успешность копий, возможность восстановления или выгрузку в удалённое
Object Storage. Watchdog также не проверяет здоровье MySQL новой Таксимо и
серверного моста РУМЕКС.

## Разработка и проверка

Зависимости Python перечислены в `fotonych-bot/requirements.txt`: `maxapi`,
`openai`, `python-dotenv`, `aiohttp`, `openpyxl`, `PyMySQL`.

Текущие модульные проверки новой границы legacy/новой Таксимо запускаются так:

```bash
python3 -m py_compile \
  fotonych-bot/taksimo_legacy_reader.py \
  fotonych-bot/taksimo_legacy_archive.py \
  fotonych-bot/taksimo_new_store.py \
  fotonych-bot/taksimo_new_api.py
node --check web/taksimo-new/app.js
git diff --check
python3 -m unittest \
  tests.test_taksimo_legacy_reader \
  tests.test_taksimo_legacy_archive \
  tests.test_taksimo_new_store \
  tests.test_taksimo_new_api
```

В текущем локальном окружении целевая проверка прошла: 24 теста успешны, 6
пропущены из-за отсутствующего `aiohttp`. Полный набор тестов дополнительно
зависит от `maxapi`, `openpyxl` и `aiohttp`; зависимости для этой проверки не
устанавливались. Миграции и production-проверки не выполнялись.

### Неподвижные правила разработки

1. Не изменять legacy-код и не писать в `data/taksimo.db` ради новой Таксимо.
2. Доступ новой Таксимо к legacy SQLite должен быть только кратковременным и
   `mode=ro`.
3. Не добавлять прямой доступ новой Таксимо к БД РУМЕКС и наоборот; бизнес-факты
   проходят только через `rumex_taksimo_bridge.py`.
4. Не смешивать сессии и права legacy Таксимо, новой Таксимо, бухгалтеров,
   диспетчера и управления РУМЕКС.
5. Подтверждённые операции исправлять новым событием/отменой, а не скрытым
   переписыванием истории.
6. Не коммитить `.env`, секреты, базы данных, WAL/SHM, журналы и прочие
   runtime-данные; добавлять в индекс только явные целевые пути.
7. Перед развёртыванием отдельно проверить миграции, резервное копирование,
   восстановление, права MySQL, Nginx и фактически запущенные сервисы.

## Открытые эксплуатационные вопросы

- Согласовать дату X и бизнес-процедуру точного архивирования legacy Таксимо.
- Проверить `009` на целевой версии MySQL до применения.
- Подтвердить производственную схему legacy SQLite: она пока проверялась только
  синтетическими тестами, без просмотра рабочей БД.
- Утвердить поведение позиции вагона при повторном сохранении приёмки, когда
  блоки из вагона удаляются или заменяются.
- Включить наблюдаемость новой MySQL и моста РУМЕКС, поскольку текущий watchdog
  покрывает только legacy API.
- Организовать проверяемое удалённое хранение резервных копий и тесты
  восстановления.
- Провести отдельный read-only аудит сервера, если требуется узнать реальные
  службы, cron/systemd, конфигурацию Nginx, сертификаты, БД и актуальную ревизию.
