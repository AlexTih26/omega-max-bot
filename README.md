# РУМЕКС / Таксимо

Единая программа для логистики ЖБИ: диспетчерская РУМЕКС, бухгалтерия
«Омега-М», площадка Таксимо и администрирование. Программа ведёт документы,
физические блоки, машины, вагоны и историю перемещений в одной MySQL-базе.

- **Версия документа:** 1.1
- **Дата:** 13.10.2026
- **Стратегия перехода:** развиваем существующую схему MySQL `taksimo_new`;
  новые изменения структуры начинаются только с миграций `014+`.

> ## Статус этого документа
>
> Этот README является нормативным контрактом **целевой единой программы**:

> и закрытые настройки без отдельного явного разрешения.

## 1. Назначение и границы

### 1.1. Что решает программа

Система отвечает на три вопроса для каждого блока и рейса:

1. Где груз находится сейчас.
2. Кто отвечает за следующий шаг.
3. Какой подтверждённый факт или документ нужен дальше.

Рабочие места остаются разделёнными по ролям, но данные и история едины:

```text
Диспетчер РУМЕКС
    -> Бухгалтер «Омега-М»
        -> Диспетчер РУМЕКС: печать и передача документов
            -> Оператор Таксимо
                -> Вагон / Кодар / БТС Восток / возврат вагона
```

### 1.2. Что было и что становится

Репозиторий вырос из MAX-бота и нескольких самостоятельных контуров: legacy
Таксимо на SQLite, документного РУМЕКС-реестра на SQLite и новой Таксимо на
MySQL. Между РУМЕКС и новой Таксимо временно действует мост.

Целевое состояние:

```text
одна программа
    +-- одна MySQL-схема `taksimo_new`
    +-- одна авторизация с ролями и точечными разрешениями
    +-- документы: рейс, ТТН, ЭР
    +-- физика: блок, площадка, вагон, Кодар, БТС Восток
    +-- неизменяемая история и устойчивые уведомления
```

После даты переключения X мост `rumex_taksimo_bridge.py` и отдельный
документный контур РУМЕКС перестанут быть бизнес-границей. До даты X они
продолжают работать по действующим ограничениям переходного периода.

### 1.3. Legacy Таксимо

Старая Таксимо (`data/taksimo.db`) **не изменяется**. Она является источником
правил площадки, сетки, тупиков и накопленного опыта, пока новая программа её
не заменит.

До даты X новая программа может получать только согласованные проекции legacy
данных и только через `taksimo_legacy_reader.py`:

- SQLite URI с `mode=ro`;
- короткое подключение с таймаутом не более двух секунд;
- одна read-only транзакция на целостный снимок;
- никаких `INSERT`, `UPDATE`, `DELETE`, схемных изменений или прямого доступа
  нового кода к `data/taksimo.db`.

Разрешённые проекции: машины, вагоны, слоты, блоки, блоки площадки, сессии,
отправленные блоки и история вагонов. Прямая репликация legacy-схемы в новой БД
не допускается: новая модель хранит только согласованные доменные сущности и
историю.

## 2. Целевой стек

| Слой | Выбор | Назначение |
| --- | --- | --- |
| Язык | Python 3.11+ | Асинхронный ввод-вывод, типы, стандартная библиотека |
| HTTP API | FastAPI | Роуты, dependency injection, OpenAPI, WebSocket |
| Валидация | Pydantic v2 | Входные команды, ответы, проверка доменных значений |
| БД | MySQL 8, InnoDB, `utf8mb4` | Транзакции, индексы, ограничения и JSON |
| Драйвер | `asyncmy` | Асинхронный пул и параметризованный чистый SQL |
| Фронтенд | Vanilla JS, ES modules, Web Components | Быстрый интерфейс без бандла и тяжёлого фреймворка |
| Стили | CSS Custom Properties, Container Queries | Единая тема и адаптация компонентов |
| Реалтайм в браузере | WebSocket FastAPI | Живые уведомления и обновление карточек |
| Уведомления MAX | MySQL outbox + отдельный воркер | Гарантированные повторы без потери бизнес-факта |
| Тесты | `unittest` | Единый стиль с существующими тестами репозитория |

### 2.1. Правило версий

«Последняя версия» не является воспроизводимой зависимостью. При добавлении
FastAPI-контура версии фиксируются совместимыми диапазонами в зависимостях,
например:

```text
fastapi >= 0.115, < 1
pydantic >= 2, < 3
asyncmy >= 0.2, < 1
```

Точные минимальные версии утверждаются только после локальной проверки Python
3.11 и текущей MySQL 8. Зависимости не устанавливаются, не обновляются и не
добавляются в production без отдельного разрешения.

### 2.2. Что не добавляем без нового архитектурного решения

- ORM: SQLAlchemy, Django ORM и аналоги. Доступ к БД — только через
  параметризованный SQL и явные транзакции.
- React, Vue, Angular и клиентский бандлер.
- Docker, Kubernetes и автоматический deployment.
- `pytest`: тестовый набор остаётся на `unittest`.
- Новые функции единой программы в `aiohttp`. Существующий `aiohttp`-контур
  продолжает обслуживать старые маршруты только до завершения перехода.

Это не означает, что существующие зависимости исчезают немедленно. Сейчас в
репозитории есть `aiohttp` и `PyMySQL`; FastAPI и `asyncmy` заменяют их только
в новом едином HTTP-контуре по этапам, без смешивания владельцев маршрутов.

### 2.3. Стиль кода

- Python: PEP 8, `from __future__ import annotations`, полные type hints в
  публичных функциях и понятные docstring для неочевидной логики.
- Функция решает одну задачу; длинный сценарий разбивается на валидацию,
  загрузку данных, транзакционную команду и формирование ответа.
- SQL параметризован. Конкатенация пользовательского ввода в SQL запрещена.
- Связанные изменения актуального состояния, истории и outbox выполняются в
  одной явной транзакции.
- Логи пишутся через `logging`, не через `print`; пароли, токены, PIN, cookie,
  содержимое документов и персональные данные целиком в логи не попадают.

## 3. Архитектура и переход

### 3.1. Целевая схема

```text
Браузер / MAX mini-app
        |
        v
Nginx: HTTPS, статика `web/`
        |
        +--> FastAPI: HTTP API и WebSocket
        |       |
        |       v
        |   MySQL 8 / InnoDB / схема `taksimo_new`
        |       |
        |       +--> бизнес-таблицы, история, outbox
        |
        +--> MAX-воркер: доставляет записи outbox в чат
```

FastAPI обслуживает только единый логистический API. MAX-бот является внешним
потребителем уведомлений, а не источником истины: сбой MAX не отменяет
сохранённый рейс, приёмку или событие вагона.

WebSocket предназначен для браузера. Он помогает пользователю увидеть новое
событие без обновления страницы, но не заменяет API, журнал и outbox.

### 3.2. Владелец данных

| Данные | Единственный владелец после перехода |
| --- | --- |
| Учётки, роли, сессии, права | MySQL `taksimo_new` |
| Машины, водители, перевозчики, вагоны и схемы | MySQL `taksimo_new` |
| Рейс, ТТН, ЭР и печатные копии | MySQL `taksimo_new` |
| Блок, его положение и история | MySQL `taksimo_new` |
| Позиция вагона и жизненный цикл | MySQL `taksimo_new` |
| Аудит и очередь уведомлений | MySQL `taksimo_new` |
| Legacy-данные до X | legacy SQLite, read-only источник |

### 3.3. Границы до даты X

Пока новый FastAPI-контур и данные не переведены полностью:

1. РУМЕКС SQLite и MySQL `taksimo_new` не подключаются к БД друг друга
   напрямую.
2. Бизнес-обмен между ними проходит только через
   `fotonych-bot/rumex_taksimo_bridge.py` и его служебный HTTP-контракт.
3. Авторизации legacy Таксимо, новой Таксимо, бухгалтеров РУМЕКС, тестового
   диспетчера и управления РУМЕКС не смешиваются.
4. Новая функциональность единой программы создаётся рядом с legacy кодом; она
   не меняет живые legacy-маршруты без утверждённого этапа перехода.
5. `taksimo_new_notify.py` не расширяется. Новый способ доставки MAX-сообщений
   строится отдельным outbox-воркером, когда к нему перейдёт ответственность.

## 4. Роли, учётки и доступ

### 4.1. Четыре типа ролей

| Роль | Кабинет | Назначение |
| --- | --- | --- |
| `admin` | Администратор | Справочники, учётки, точечные права, аудит и здоровье системы |
| `dispatcher` | Диспетчер РУМЕКС | Машина, блоки, рейс, ТТН, передача водителю |
| `accountant` | Бухгалтер «Омега-М» | Проверка документов, ручная ЭР, разрешение отгрузки |
| `operator` | Оператор Таксимо | Приёмка, площадка, вагон, Кодар, БТС Восток и возврат |

Роль — это набор полномочий, а не идентификатор конкретного человека. В системе
могут быть несколько диспетчеров, бухгалтеров и операторов. Отображаемое имя
пользователя обязательно попадает в историю действия.

### 4.2. Учётки и текущая схема

В существующей схеме `tn_operator_accounts` ранее код роли одновременно был
уникальным идентификатором учётки (`operator1`, `accountant1` и так далее).
Это не позволяет безопасно создать второго человека той же роли.

Первый этап `014+` обязан разделить эти понятия:

- уникальный логин идентифицирует учётку;
- роль (`admin`, `dispatcher`, `accountant`, `operator`) задаёт базовые права;
- отображаемое имя и при необходимости смена отличают конкретных сотрудников;
- уникальность роли на одну запись удаляется только вместе с обновлением
  авторизации и тестов;
- старые коды не удаляются без явной миграции существующих сессий и маршрутов.

### 4.3. Разрешения

Роль выдаёт права по умолчанию. Администратор может задавать точечные
исключения пользователю: просмотр, редактирование и печать для конкретной
возможности, например `trip.create`, `trip.print`, `wagon.transition`.

Целевая модель БД:

```text
role_permissions     role_code + capability + can_view/can_edit/can_print
account_permissions  account_id + capability + nullable overrides
```

Решение о доступе принимает только серверная FastAPI dependency. Скрытая
кнопка или вкладка на фронтенде — удобство интерфейса, но не механизм защиты.

Пример целевого маршрута:

```python
@router.post("/api/v1/dispatcher/trips")
async def create_trip(
    command: CreateTrip,
    actor: Actor = Depends(require_permission("trip.create", "edit")),
) -> TripResponse:
    return await trip_service.create(command, actor)
```

### 4.4. Правило полномочий

- Администратор не переписывает подтверждённую историю.
- Диспетчер не подтверждает ЭР за бухгалтера.
- Бухгалтер не подменяет физическую приёмку оператора.
- Оператор не создаёт или не переиздаёт ТТН.
- Разрешение на критический переход вагона выдаётся отдельной capability, а не
  зашивается навсегда в имя `operator1`.

## 5. Доменная модель

### 5.1. Блок

Блок — минимальная физическая единица. Его сквозной идентификатор создаётся
диспетчером при создании рейса и сохраняется всю жизнь.

| Свойство | Правило |
| --- | --- |
| Внутренний идентификатор | Не меняется после создания |
| Человекочитаемый ключ | Нормализованные `буква + номер`, например `A-901` |
| Буква | Только `A`, `B`, `C`, `D`, `E`, `F`, `K` |
| Суффикс | `""`, `к`, `а`, `тк`, `скол` |
| Вес и стоимость | Значения справочника по умолчанию, снимок в рейсе и документе |
| История | Каждое подтверждённое перемещение — отдельное событие |

Веса, утверждённые для справочника:

```text
A = 7780 кг    B = 7900 кг    C = 8080 кг    D = 8080 кг
E = 7900 кг    F = 7780 кг    K = 3850 кг
```

Номер не используется отдельно от буквы как уникальный идентификатор: `A-901`
и `K-901` — разные ключи. Канонический ключ состоит только из буквы и номера;
суффикс хранится отдельным свойством и не создаёт второй блок: `A-901` и
`A-901к` ссылаются на один паспорт `A-901`. Полный ключ, а не последние три
цифры машины или свободный текст, используется в API и в связях БД.

### 5.2. Машина, водитель и перевозчик

- Машина — справочник с уникальным государственным номером.
- Хвост номера помогает быстро найти машину, но не является её уникальным
  идентификатором: при совпадении пользователь выбирает полную карточку.
- Перевозчик и водитель являются справочниками, но рейс хранит собственный
  снимок имени, ИНН, номера прав и номера машины.
- Правка справочника никогда не меняет уже оформленную ТТН, ЭР или историю
  рейса.

### 5.3. Рейс и документы

Рейс связывает машину, водителя, перевозчика и набор блоков. ТТН получает
номер один раз и не переиздаётся поверх старого номера. Для исправления после
подтверждения создаётся отмена либо новая ревизия по согласованному правилу,
а не скрытое изменение исходного документа.

Экспедиторская расписка (ЭР) — ручной документ бухгалтера. Сотрудник переносит
данные в Диадок или Контур и отмечает в системе только факты «отправлено» и
«вернулось». Интеграция с ЭДО не входит в целевой объём.

### 5.4. Площадка и вагон

| Объект | Правило |
| --- | --- |
| Складская сетка | `13 x 25`, максимум четыре блока в ячейке |
| Рабочие зоны | `ХРАНЕНИЯ`, `ГРУЗОВОЙ`, `ТУРАН`, третий тупик |
| Системные зоны | `В КОДАР`, `БТС ВОСТОК` |
| Тупики | `Грузовой`, `Туран`, `Третий`; по 10 позиций |
| Схема вагона | Отдельная сущность, назначается до постановки порожнего вагона |

Схемы вагона определяют допустимый состав и максимум блоков:

| Код | Максимум | Допустимые буквы |
| --- | ---: | --- |
| `scheme1` | 9 | `A-F` и `K`; состав описан ниже |
| `scheme2` | 16 | `K` |
| `scheme3` | 8 | `A-F` |

Для `scheme1` обязательны семь блоков типов `A`, `B`, `C`, `D`, `E`, `F` и
ровно один `K`. Два оставшихся места занимают любые дополнительные физические
блоки типов `A-F`: их буквы могут повторяться, но один и тот же канонический
ключ блока нельзя загрузить в вагон дважды.

В существующей миграции `010` у `scheme1` указано устаревшее
`allowed_letters = 'ABCDEF'`, которое не отражает обязательный `K`. Файл `010`
не изменяется: первая относящаяся к этому миграция `014+` корректирует
справочник и добавляет проверку полного состава на уровне команды и тестов.

Схема принадлежит вагону в конкретном цикле, а не слоту тупика. Перестановка
между тупиками — отдельный физический факт истории.

### 5.5. Неизменяемость

Подтверждённые бизнес-факты не переписываются:

- актуальная проекция объекта может меняться внутри допустимой команды;
- `tn_events`, `tn_block_history` и журналы аудита получают только новые
  записи;
- исправление фиксируется новой ревизией, отменой с причиной или компенсационным
  событием;
- `DELETE` для очереди, документа или истории не используется как способ
  «стереть ошибку»;
- справочники деактивируются (`active = 0`), если запись больше нельзя
  использовать.

## 6. Сквозной процесс

### 6.1. Документный и физический потоки

```text
1. Диспетчер выбирает полную карточку машины из очереди.
2. Диспетчер создаёт рейс и строки блоков.
3. Система фиксирует снимки веса, стоимости, водителя и перевозчика.
4. Диспетчер получает номер ТТН и печатает четыре экземпляра.
5. Бухгалтер проверяет рейс и вручную отражает ЭР.
6. Бухгалтер разрешает передачу документов водителю.
7. Диспетчер печатает/выдаёт комплект и отмечает выезд машины.
8. Оператор Таксимо видит ожидаемую машину и подтверждает приёмку блоков.
9. Оператор размещает блоки на площадке либо грузит в вагон.
10. Вагон проходит цикл Таксимо -> Кодар -> БТС Восток -> возврат.
11. Порожний вагон получает место в тупике и новую схему перед следующим циклом.
12. После завершения приёмки машина автоматически возвращается в очередь
    Северомуйска отдельным подтверждённым событием.
```

Ожидаемая и фактическая приёмка — одна сущность `tn_intakes`, а не две
параллельные карточки. Ожидание хранит плановую дату и ожидаемые строки в
`tn_expected_intake_lines`; факт сохраняется в тех же приёмке и её строках
`tn_intake_lines`, включая результат по каждому блоку. В существующей модели
используются `planned_arrival_at`, `arrived_at`, `crane_started_at`,
`crane_ended_at` и `confirmed_at`; статусы: `expected`, `draft`,
`in_progress`, `confirmed`, `discrepancy`.

Автоматический возврат в очередь — целевое правило миграции `015+`. Он
выполняется в одной транзакции только после фиксации окончания работы крана и
итога по всем строкам приёмки (`received`, `missing` или `damaged`), а не после
сохранения первого блока. Команда добавляет событие возврата, аудит и outbox;
она не удаляет приёмку, рейс или историю машины.

### 6.2. Автоматы состояний

Один общий `status` на все документы и физические операции недостаточен. В
миграциях `014+` документный и физический статусы должны быть разделены.

**Документы рейса:**

```text
draft -> ttn_issued -> ttn_printed -> accountant_review
      -> er_sent -> approved -> documents_printed
      -> handed_to_driver
      -> cancelled
```

**Движение машины:**

```text
queued -> assigned_to_trip -> departed -> arrived_taksimo
       -> received -> returned_to_queue
```

**Блок:**

```text
declared -> in_transit -> at_yard -> in_wagon
         -> in_kodar -> unloaded_bts_east
```

**Вагон:**

```text
forming -> loaded -> in_transit -> at_kodar
        -> unloaded_bts_east -> returned_empty -> forming
```

Переход может выполнить только разрешённая роль и только при выполненных
предпосылках. Например, нельзя выехать до передачи документов, а невозможно
загрузить в вагон блок, который не принят на площадке.

### 6.3. Снимки

В системе различаются справочник и подтверждённый факт:

- справочник типа блока задаёт вес и стоимость по умолчанию;
- строка рейса сохраняет свои `weight_snapshot` и `price_snapshot`;
- рейс сохраняет снимок машины, водителя и перевозчика;
- ТТН и ЭР хранят неизменяемые данные выдачи;
- событие всегда содержит автора, время и необходимые данные на момент факта.

## 7. Кабинеты и API

### 7.1. Правила API

- Базовый путь нового контура: `/api/v1`.
- Идентификаторы в URL — публичные UUID/ключи, если внутренний числовой ID не
  является частью безопасного контракта.
- Все входные тела описаны Pydantic v2-моделями; сервер возвращает
  структурированную ошибку с кодом и безопасным сообщением.
- Изменяющие команды используют `POST` для бизнес-действий, а не универсальный
  `PUT status`. Переход должен быть названным и проверяемым.
- Списки используют ограничение размера и cursor-пагинацию. Неконтролируемые
  ответы «вся история» запрещены.
- Идемпотентные внешние команды принимают `Idempotency-Key` и сохраняют ключ в
  БД. Повтор не создаёт второй рейс или второе уведомление.
- Физический `DELETE` для бизнес-объектов не публикуется. Отмена, деактивация
  и архивирование выполняются именованными `POST`-командами с причиной,
  актором и аудитом.

## 8. БД, события и миграции

### 8.1. Принципы MySQL

- MySQL 8, InnoDB, `utf8mb4`, UTC в `DATETIME(6)`.
- Все связи фиксируются внешними ключами с осмысленным `RESTRICT` или `SET NULL`.
- Ограничения `CHECK`, уникальные ключи и триггеры защищают инварианты у самой
  БД, а Pydantic повторяет проверку на границе HTTP.
- Драйвер `asyncmy` использует пул. Запрос получает соединение на краткое время
  и гарантированно возвращает его в пул.
- Любая команда, меняющая бизнес-факт, работает в одной транзакции.

### 8.2. Существующая основа `001–013`

Новая схема уже не начинается с нуля. В `migrations/taksimo_new/` существуют:

| Группа | Содержание |
| --- | --- |
| `001–004` | Базовая MySQL-модель приёмок, блоков, вагонов, сессий и отмен |
| `005–006` | Переходный мост РУМЕКС, физический цикл, inbox/outbox и триггеры |
| `007` | Возврат порожнего вагона и триггеры жизненного цикла |
| `008` | Неизменяемые вложения приёмки и копии ТТН |
| `009` | Позиции трёх тупиков и read-only архив legacy-снимка |
| `010` | Справочники, роли, машины, вагоны, сетка `13 x 25`, журнал действий |
| `011` | Логины и учётные записи ролей |
| `012` | Рейсы, ТТН, четыре копии, ЭР и связь с приёмкой |
| `013` | Паспорт блока, история блока и история машины |

В каталоге исторически есть два файла с номером `007`; существующие миграции не
переименовываются и не переписываются. Новые файлы получают следующий свободный
номер `014+`.

### 8.3. Основные таблицы единой модели

| Область | Уже есть в MySQL | Развитие `014+` |
| --- | --- | --- |
| Учётки | `tn_operator_accounts`, `tn_operator_sessions`, `tn_operator_login_attempts` | Несколько учёток одной роли, точечные права |
| Справочники | `tn_block_types`, `tn_carriers`, `tn_drivers`, `tn_vehicles`, `tn_wagon_fleet`, `tn_dead_ends` | Полный CRUD с soft-delete и аудитом |
| Рейс и документы | `tn_trips`, `tn_trip_blocks`, `tn_ttn_numbers`, `tn_ttn_copies`, `tn_expedition_receipts` | Раздельные автоматы документов и транспорта |
| Физика | `tn_intakes`, `tn_blocks`, `tn_wagons`, `tn_wagon_loads` | Единая очередь машины, команды приёмки и размещения |
| Позиции вагонов | `tn_wagon_yard_slots`, `tn_wagon_position_history` | Контроль схемы перед постановкой и перестановок |
| История | `tn_events`, `tn_block_registry`, `tn_block_history`, `tn_action_log` | Защита append-only и единые ссылки на акторов |

Названия не дублируются второй схемой `users`, `events` или `blocks`: выбран
путь развития существующей базы `taksimo_new`, а не параллельный чистый проект.
Отдельная таблица `tn_vehicle_history` не требуется: история машины строится из
`tn_trips`, для чего миграция `013` добавила индексы по машине и дате.

### 8.4. Предлагаемая последовательность миграций

Имена и состав миграций утверждаются перед реализацией, но порядок должен быть
таким:

| Номер | Цель | Ключевой результат |
| --- | --- | --- |
| `014` | Учётки и права | Роль отделена от пользователя; добавлены матрица и overrides |
| `015` | Очередь и состояния рейса | Отдельные документный и транспортный автоматы, завершение приёмки и автоматический возврат машины |
| `016` | Аудит и идемпотентность | Защита событий от изменения, команды с ключом повтора |
| `017` | FastAPI-outbox | Доставка в MAX и события браузеру без зависимости от legacy notify |
| `018+` | Перенос и дата X | Только после утверждения процедуры сверки и отката |

Каждая миграция должна быть малой, повторяемой через уже существующую таблицу
учёта миграций и сопровождаться отдельным `unittest`-набором. Миграции не
запускаются приложением автоматически.

### 8.5. Транзакционная команда

Изменение уровня «машина выехала» должно быть атомарным:

```text
BEGIN
  1. Проверить сессию, роль, права и допустимость статуса.
  2. Заблокировать рейс/машину точечным SELECT ... FOR UPDATE.
  3. Обновить актуальную проекцию рейса и машины.
  4. INSERT в историю событий с актором и снимком данных.
  5. INSERT в outbox с идемпотентным ключом.
COMMIT

После COMMIT воркер доставляет уведомление с безопасными повторами.
```

Ошибка на любом шаге до `COMMIT` откатывает всё. Ошибка доставки после `COMMIT`
оставляет строку outbox ожидающей повторной попытки и не отменяет выезд.

## 9. Уведомления и WebSocket

### 9.1. Надёжные уведомления MAX

Уведомление MAX не отправляется прямо из HTTP-обработчика. Бизнес-команда пишет
в `tn_notification_outbox` в той же транзакции, что и факт. Отдельный воркер:

1. берёт недоставленные сообщения ограниченной пачкой;
2. отправляет их через клиент MAX;
3. сохраняет каждую попытку и безопасное описание результата;
4. отмечает доставку только после успеха;
5. повторяет временные ошибки без создания дубликата по `idempotency_key`.

Обязательные события MAX целевой программы:

| Событие | Получатель |
| --- | --- |
| `trip.departed` | Чат диспетчерской / ответственный оператор |
| `intake.confirmed` | Чат Таксимо / ответственный диспетчер |
| `intake.discrepancy` | Ответственный диспетчер и бухгалтер |
| `vehicle.returned_to_queue` | Чат диспетчерской |
| `wagon.dispatched` | Чат логистики |
| `wagon.arrived_kodar` | Чат логистики |
| `wagon.unloaded_bts_east` | Чат логистики |
| `wagon.returned_empty` | Чат логистики |
| `trip.returned_for_correction` | Ответственный диспетчер |

Расширенные события (`intake.arrived`, `intake.crane_started`,
`intake.crane_ended`, `block.placed`, `block.loaded_to_wagon`) включаются только
после назначения получателя и правила, чтобы не превратить рабочий чат в поток
технического шума. Имена выше — целевой контракт для FastAPI-outbox; текущие
переходные имена событий в `taksimo_new_store.py` могут отличаться до миграции.

Сообщение содержит причину и ссылку на карточку объекта. Оно не заменяет
действие в системе и не содержит секретов.

### 9.2. WebSocket для браузера

Целевой канал: `GET /ws/notifications` после проверки сессионной cookie и
Origin. Сервер сам определяет темы по правам пользователя; клиент не может
подписаться на «чужую» роль только параметром URL.

Пример безопасного полезного сообщения:

```json
{
  "type": "trip.departed",
  "event_id": "uuid",
  "occurred_at": "2026-10-13T12:00:00Z",
  "subject": {"kind": "trip", "id": "uuid"}
}
```

Клиент после получения сообщения перечитывает карточку через API. WebSocket не
передаёт PIN, токен, полное содержимое ТТН или доверенный статус без проверки.
При разрыве соединения интерфейс делает ограниченные повторы подключения и
остаётся работоспособным через обычные HTTP-запросы.

## 10. Фронтенд и UX

### 10.1. Целевая структура

web/unified/
├── index.html
├── login.html
├── shared/
│   ├── api.js                 HTTP-клиент и разбор ошибок
│   ├── auth.js                сессия и эффективные разрешения

│   ├── app-shell.js

Это целевая структура, а не команда немедленно создать все файлы. Каждый новый

### 10.2. Общие принципы

- Mobile-first: на площадке основное действие — тап, а не курсор мыши.
- Один экран — одна главная задача; сложный путь разбивается на короткие шаги.
- Обязательные поля, текущий статус и следующий допустимый шаг видны до
  отправки формы.
- Опасные операции требуют подтверждения, причины и отображения последствий.
- Таблицы поддерживают поиск, фильтр, курсорную пагинацию и переход в карточку.
- Все элементы доступны с клавиатуры, имеют видимый фокус и достаточный
  контраст; текст статуса не заменяется одним цветом.

### 10.3. Стили

Общие значения определяются один раз через CSS Custom Properties:

```css
:root {
  --color-waiting: #667085;
  --color-active: #175cd3;
  --color-success: #067647;
  --color-warning: #b54708;
  --color-danger: #b42318;
  --space-2: 0.5rem;
  --space-4: 1rem;
  --radius-card: 0.75rem;
}
```

Container Queries адаптируют компонент к его ширине, а не только к ширине всего
экрана. Внешние UI-библиотеки и препроцессоры не добавляются.

### 10.4. Кабинеты

- **Администратор:** сводка, учётки и права, справочники, очередь, аудит.
- **Диспетчер:** очередь машин слева, активный рейс и блоки справа, понятный
  путь ТТН -> бухгалтер -> передача -> выезд.
- **Бухгалтер:** реестр ожидающих документов, карточка рейса, копирование
  данных для ЭДО, ЭР и разрешение/возврат.
- **Оператор:** ожидаемые машины, приёмка, сетка площадки, три тупика по десять
  позиций и карточка вагона с историей.

## 11. Быстродействие и надёжность

### 11.1. Правила производительности

Скорость системы обеспечивается измеримыми решениями, а не названием
фреймворка:

- `asyncmy` использует ограниченный пул подключений; соединение не открывается
  заново на каждую вложенную операцию.
- Транзакции короткие: нельзя держать блокировку во время генерации XLSX,
  HTTP-вызова MAX или ожидания пользователя.
- В реестрах всегда есть `LIMIT`, cursor и индекс под фильтр/сортировку.
- Нет `SELECT *` в крупных списках, N+1-запросов и загрузки документов вместе
  с табличным реестром.
- Внешние документы и большие вложения скачиваются отдельным маршрутом.
- Перед добавлением тяжёлого запроса проверяется его план (`EXPLAIN`) на
  обезличенной локальной или тестовой БД.
- Индекс добавляется вместе с новым рабочим фильтром, историей или внешним
  ключом, а не «на всякий случай».

### 11.2. Целостность и отказоустойчивость

- Переход статуса проверяется сервером и БД, а не только интерфейсом.
- Внешний сбой не отменяет уже зафиксированный факт.
- Повтор одной команды с одинаковым ключом идемпотентности возвращает исходный
  результат, не создавая вторую запись.
- Печатная копия хранит SHA-256 и размер; номер ТТН уникален на рейс и в общей
  нумерации.
- Все даты хранятся в UTC; отображение использует рабочий часовой пояс на
  уровне ответа/интерфейса.
- Снимки справочников и история защищают прошлые документы от будущей правки.

## 12. Безопасность

### 12.1. Аутентификация и сессии

- Вход: уникальный логин и PIN длиной 6–12 цифр.
- PIN хранится только как `scrypt`-хэш; PIN, пароль и исходный токен никогда не
  сохраняются в аудит или лог.
- Сессия создаётся из криптографически случайного токена, а в БД хранится только
  его хэш, срок, время последней активности и признак отзыва.
- Cookie: `HttpOnly`, `Secure`, `SameSite=Lax`, узкий `Path`; для изменяющих
  cookie-запросов предусмотрена CSRF-защита.
- Неуспешные входы ограничиваются по адресу и учётке; успешный и неуспешный
  входы попадают в журнал без секретных значений.

### 12.2. API и WebSocket

- Каждая изменяющая HTTP-команда требует проверку сессии, роли и capability.
- SQL всегда параметризован.
- Pydantic отвергает лишние и некорректные поля там, где это важно для команды.
- Ошибки не раскрывают SQL, стек, наличие чужой учётки или внутренние секреты.
- WebSocket проверяет cookie, Origin и права до подписки на события.

### 12.3. Эксплуатационные запреты

Без отдельного разрешения нельзя:

- читать `.env`, private-конфигурации, токены, PIN, рабочие БД, логи и backup;
- применять миграции, устанавливать зависимости, выполнять deployment или
  рестартовать сервисы;
- менять legacy SQLite или расширять `taksimo_new_notify.py`;
- добавлять в Git базы, WAL/SHM, журналы, виртуальные окружения, секреты и
  runtime-состояние.

## 13. Разработка, тесты и Git

### 13.1. Структура будущего FastAPI-модуля

Новый код не должен дублировать один и тот же сценарий по папкам кабинетов.
Кабинет задаёт маршруты и права, домен владеет операцией. Ниже приведена
рекомендуемая структура, если отдельным решением будет выбран корневой каталог
`app/`:

```text
app/
├── main.py                    FastAPI, lifespan, маршруты
├── api/                       HTTP-роуты кабинетов и dependencies
├── auth/                      сессии, роли, permissions, CSRF
├── domain/
│   ├── trips/                 рейс, ТТН, ЭР, состояния документов
│   ├── blocks/                паспорт и история блока
│   ├── intakes/               ожидаемая и фактическая приёмка
│   ├── wagons/                схема, позиции, жизненный цикл
│   └── catalogs/              машины, водители, перевозчики
├── repositories/              asyncmy и параметризованный SQL
├── services/                  транзакционные команды
├── outbox/                    MAX-доставка и фоновые повторы
└── ws/                        авторизованный real-time браузера
```

Пока место будущего FastAPI-каталога не утверждено, существующие модули
`fotonych-bot/taksimo_new_*.py` и `migrations/taksimo_new/` остаются местом
развития MySQL-модели. Новое дерево создаётся только отдельной задачей вместе с
первым маршрутом FastAPI.

### 13.2. Тесты

Тесты пишутся на `unittest`:

- доменные: нормализация блока, переходы статусов, снимки и разрешения;
- репозитории: параметризованные запросы, транзакции и идемпотентность;
- API: авторизация, `401`, `403`, `400`, `404`, контракты ответов;
- интеграционные: outbox и повтор после неудачной доставки;
- регрессионные: каждая исправленная ошибка получает тест.

Для асинхронных сценариев используется `unittest.IsolatedAsyncioTestCase`.
Тесты не подключаются к production-БД и не требуют чтения `.env`.

После появления FastAPI-модуля минимальная проверка изменённой области:

```bash
python3 -m compileall -q app
python3 -m unittest discover -s tests -p 'test_*.py'
git diff --check
```

До этого применяются существующие целевые тесты затронутого модуля из `tests/`,
а JavaScript проверяется через `node --check` для изменённых файлов. Команды
запускаются только при наличии соответствующего интерпретатора и зависимостей;
отсутствие среды указывается как блокер, а не скрывается.

### 13.3. Правила Git

1. Перед изменением общей логики найти все использования и связанные тесты.
2. Сначала прочитать затрагиваемый файл и текущий `git diff`.
3. Не трогать и не откатывать чужие изменения рабочего дерева.
4. Перед коммитом выполнить `git diff --check`, целевые тесты и `git status`.
5. Добавлять в индекс только целевые пути: `git add README.md` или
   `git add <точные пути>`. Команда `git add .` запрещена.
6. Не коммитить рабочие базы, WAL/SHM, лог-файлы, документы пользователей,
   ключи, токены и временные файлы.

## 14. План перехода

### Этап 0. Зафиксировать контракт

Этот README задаёт целевую модель. До создания FastAPI не надо изображать, что
`aiohttp` уже отключён или что `asyncmy` уже установлен: это будущий интерфейс,
а не зафиксированный production-факт.

### Этап 1. Развить MySQL `014+`

1. Отделить роль от учётной записи и добавить точечные права.
2. Ввести явную очередь машин и раздельные автоматы документов/транспорта.
3. Укрепить append-only аудит и идемпотентность команд.
4. Добавить или адаптировать тесты каждой миграции.

### Этап 2. Появление FastAPI рядом с legacy HTTP

1. Добавить зависимости после отдельной проверки.
2. Создать минимальный `app/` и `GET /api/v1/auth/me`.
3. Перенести один завершённый вертикальный сценарий целиком: схема, команда,
   тест, API, страница и аудит.
4. Не дублировать запись одного бизнес-факта одновременно через FastAPI и
   legacy-маршрут.

### Этап 3. Кабинеты и outbox

1. Администратор: учётки, справочники, права и аудит.
2. Диспетчер: очередь, рейс, ТТН, передача водителю.
3. Бухгалтер: ЭР и разрешение документов.
4. Оператор: приёмка, площадка, вагон и позиции.
5. Outbox-воркер: MAX и WebSocket-события после фиксации факта.

### Этап 4. Обкатка и дата X

Дата X не выбирается по готовности одного экрана. Перед ней требуются:

- согласованный перенос состояния машин, блоков, вагонов и их положений;
- измеримая сверка новой и legacy логики на согласованных примерах;
- план остановки/переключения/проверки и план отката;
- проверенные резервные копии и восстановление на нерабочей копии;
- явное разрешение на каждую production-операцию.

Только после этого бизнес-мост РУМЕКС и старые документные таблицы могут быть
выведены из рабочего пути. Legacy SQLite остаётся неизменяемым архивным
источником, а не целевой базой новой программы.

## 16. Словарь терминов

| Термин | Значение в этом документе |
| --- | --- |
| Блок | Физическое ЖБИ с неизменяемым каноническим ключом «буква + номер». |
| Суффикс блока | Отдельная отметка состояния или особенности блока; не часть его ключа. |
| Рейс | Связанный набор машины, водителя, перевозчика, блоков и документов. |
| Приёмка | Одна карточка `tn_intakes`, которая проходит путь от ожидаемого рейса до факта по строкам блоков. |
| Очередь Северомуйска | Транспортная очередь машин, из которой диспетчер назначает машину на следующий рейс. |
| Схема вагона | Правило состава и вместимости вагона в конкретном цикле, а не свойство слота тупика. |
| Кодар / БТС Восток | Этапы жизненного цикла вагона; их географический или внешний операционный контекст этот README не определяет. |
| Отмена | Завершение ошибочной операции с обязательной причиной и новым событием без удаления истории. |
| Деактивация | Исключение справочной записи из новых операций при сохранении её истории (`active = 0`). |
| Архивирование | Целевая более строгая форма вывода из работы с причиной и аудитом; не физическое удаление. |
| Outbox | Таблица событий, записываемых в одной транзакции с бизнес-фактом и доставляемых воркером с повторами. |

## Правило для разработчика и AI-агента

Перед каждой задачей определить, относится ли она к переходному legacy-контуру
или к целевой единой программе. При сомнении:

1. не трогать legacy Таксимо и рабочие данные;
2. не нарушать текущую границу РУМЕКС ↔ новая Таксимо до даты X;
3. развивать существующую MySQL-схему только миграциями `014+`;
4. сохранять историю новым событием, ревизией или отменой;
5. проверять роль, право, транзакцию, аудит и outbox для любой новой команды;
6. явно сообщать о конфликте README, миграции и кода до изменения логики.
