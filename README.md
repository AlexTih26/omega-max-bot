# OMEGA / MAX / РУМЕКС / Таксимо

Технический гид по репозиторию `omega-max-bot`: архитектура, владельцы данных,
границы интеграции, фактические потоки и правила безопасной разработки.

> **Важно.** Документ составлен по исходному коду, миграциям и шаблонам
> конфигурации репозитория. Он **не подтверждает** состояние production-сервера:
> Nginx, systemd/cron, сертификаты, применённые миграции, рабочие базы,
> резервные копии, токены, журналы и развёрнутую ревизию.
>
> Не читать `.env`, рабочие БД, журналы, токены, PIN и закрытые настройки без
> отдельного явного разрешения. Если этот документ расходится с кодом,
> источником истины является код; о расхождении нужно сообщить до изменения
> логики.

## Как пользоваться гидом

1. Определите контур-владельца данных в разделе «Состав платформы».
2. Прочитайте его раздел, основной код и соответствующие тесты.
3. Если задача пересекает РУМЕКС и новую Таксимо, сначала прочитайте раздел
   «Фактический поток РУМЕКС ↔ новая Таксимо».
4. Не нарушайте правила из раздела «Границы разработки».
5. Перед production ориентируйтесь на «Открытые эксплуатационные вопросы».

## Состав платформы

Проект вырос из MAX-бота с комментариями к постам. Основной запуск
`fotonych-bot/bot.py` объединяет MAX long polling, HTTP API и фоновые задачи.

| Контур | Назначение | Основное хранилище |
| --- | --- | --- |
| OMEGA / MAX | MAX long polling, комментарии, AI-помощник, служебные чаты и mini-app | SQLite и JSON-файлы модулей |
| Старая Таксимо | Историческая площадка: плиты, склад, тупики, вагоны | SQLite `data/taksimo.db` |
| Новая Таксимо | Отдельная PWA физической логистики, приёмки и вагонов | MySQL `taksimo_new` |
| РУМЕКС-реестр | Документные факты: диспетчер, бухгалтеры, ТТН, ЭР, перевозчики | SQLite `data/rumex_registry.db` |
| РУМЕКС-очередь | Историческая диспетчерская логика | JSON-состояние |
| Склад Мастер | Материалы, заявки и перемещения | SQLite `data/sklad_master.db` |
| Водители, материалы, ИП-документы, FOTON | Вспомогательные рабочие контуры | SQLite и JSON-файлы модулей |

Три главных логистических контура не являются одной физической базой данных:

```text
старая Таксимо: SQLite    новая Таксимо: MySQL    РУМЕКС-реестр: SQLite
```

## Серверная схема

```text
Интернет / браузер / MAX mini-app
                |
                v
       Nginx :443 (шаблоны в scripts/)
                |
                v
           aiohttp 127.0.0.1:8765  <---->  bot.py / MAX long polling
                |
                +-- старая Таксимо: SQLite data/taksimo.db
                +-- РУМЕКС-реестр: SQLite data/rumex_registry.db
                +-- новая Таксимо: MySQL taksimo_new
                +-- мост РУМЕКС <-> новая Таксимо
```

- `fotonych-bot/comments_api.py` собирает общий `aiohttp` API.
- `bot.py` запускает HTTP API, MAX long polling, бэкапы, уведомления, контроль
  сроков РУМЕКС и мост РУМЕКС ↔ новая Таксимо.
- `scripts/start-taksimo-api.sh` запускает только HTTP API без MAX polling и
  фоновых задач; это сервисный/отладочный скрипт, а не штатный перезапуск.
- В репозитории есть Nginx-шаблоны `scripts/nginx-avtmsk.ru.conf` и
  `scripts/nginx-max.avtmsk.ru.conf`. Оба используют `root /MAX_BOT/web`, поэтому
  статические файлы технически не разделены между доменами этими шаблонами.
- Наличие шаблонов не означает, что они установлены или активны на сервере.

В репозитории не обнаружены Dockerfile, Docker Compose, systemd unit и
YAML-конфигурации CI/CD. Эксплуатация описана shell-скриптами, но не
подтверждена для production.

## Границы разработки

1. **Не писать в `data/taksimo.db`.** Новый код не изменяет legacy SQLite.
2. Доступ новой Таксимо к legacy SQLite допустим только через кратковременное
   подключение `mode=ro` с таймаутом 2 секунды.
3. РУМЕКС и новая Таксимо не читают и не изменяют БД друг друга напрямую.
4. Бизнес-факты между РУМЕКС и новой Таксимо проходят только через
   `fotonych-bot/rumex_taksimo_bridge.py`.
5. Не смешивать права, cookie, секреты и сессии старой Таксимо, новой Таксимо,
   бухгалтеров РУМЕКС, диспетчера РУМЕКС и управления РУМЕКС.
6. Подтверждённую историю не переписывать скрытым `UPDATE` или `DELETE`:
   исправление оформляется новой ревизией, событием или отменой операции.
7. Не добавлять в Git `.env`, токены, PIN, БД, WAL/SHM, журналы, виртуальные
   окружения и иные runtime-файлы.
8. Не применять миграции, не перезапускать сервисы и не выполнять deployment
   без явного разрешения.

## Старая Таксимо

Старая Таксимо — исторический рабочий контур площадки.

- БД: `data/taksimo.db`, SQLite.
- Основной код:
  - `fotonych-bot/taksimo_store.py`;
  - `fotonych-bot/taksimo_store_fleet.py`;
  - `fotonych-bot/taksimo_store_materials.py`;
  - `fotonych-bot/taksimo_wagon_logic.py`;
  - `fotonych-bot/taksimo_api.py`;
  - `fotonych-bot/taksimo_auth.py`;
  - `web/taksimo.html`, `web/taksimo.js`, `web/taksimo.css`.

Доменные правила legacy-контура:

- буквы плит: `A–F`, `K`;
- суффиксы: `""`, `к`, `а`, `тк`, `скол`;
- рабочие зоны: `ХРАНЕНИЯ`, `ГРУЗОВОЙ`, `ТУРАН`, `В ПУТИ`;
- системные зоны: `В КОДАР`, `БТС ВОСТОК`;
- сетка склада: `13 × 25`;
- максимум плит в ячейке: `4`;
- максимум плит в вагоне: `9`;
- два legacy-тупика: `ГРУЗОВОЙ` и `ТУРАН`, до 10 мест каждый.

Новая Таксимо не переносит в свою модель legacy-зоны, legacy-схемы вагонов или
legacy-позиции тупиков.

## РУМЕКС-реестр

РУМЕКС является владельцем документных фактов.

- БД: `data/rumex_registry.db`, SQLite, `WAL`, `foreign_keys=ON`,
  `busy_timeout=5000`.
- Схема: `SCHEMA_VERSION = 11`.
- Основной код:
  - `fotonych-bot/rumex_registry_store.py`;
  - `fotonych-bot/rumex_registry_api.py`;
  - `fotonych-bot/rumex_registry_auth.py`;
  - `fotonych-bot/rumex_test_dispatcher_auth.py`;
  - `fotonych-bot/rumex_registry_documents.py`;
  - `fotonych-bot/rumex_registry_export.py`;
  - `fotonych-bot/rumex_registry_backup.py`;
  - `fotonych-bot/rumex_registry_notifications.py`;
  - `fotonych-bot/rumex_management_api.py`;
  - `fotonych-bot/rumex_admin_auth.py`.

Внутри одной SQLite БД РУМЕКС есть два реестра:

| Реестр | Основные таблицы | Назначение |
| --- | --- | --- |
| Боевой | `shipments`, `shipment_items`, `shipment_documents` | Основной документный поток |
| Тестовый | `test_shipments`, `test_shipment_items`, `test_shipment_documents` | Тестовая погрузка диспетчера и бухгалтерская обработка |

Роли РУМЕКС:

| Контур | Вход |
| --- | --- |
| Бухгалтеры | PIN, `Бухгалтер 1`, `Бухгалтер 2`, `Бухгалтер 3` |
| Администратор справочников | Только `Бухгалтер 1` |
| Тестовый диспетчер | Отдельная парольная сессия, cookie `rumex_test_dispatcher_auth` |
| Управление РУМЕКС | Отдельная cookie-сессия, вход из MAX или по паролю |

`rumex_dispatcher_accounts` хранит учётные записи диспетчеров. Серверные сессии
тестового диспетчера хранятся отдельно в `test_dispatcher_sessions`.

Стартовые номинальные веса блоков в РУМЕКС:

```text
A=7780  B=7900  C=8080  D=8080  E=7900  F=7780  K=3850 кг
```

Они помечены в коде как предварительные. Уже оформленные строки документов
хранят собственный снимок веса, поэтому изменение справочника не меняет историю.

## Фактический поток РУМЕКС ↔ новая Таксимо

### Боевой реестр

Для основного реестра последовательность реализована так:

```text
РУМЕКС: диспетчер и бухгалтер
    -> подтверждение ЭР
    -> подтверждённый снимок РУМЕКС
    -> мост
    -> ожидаемая приёмка в новой Таксимо
    -> физические факты новой Таксимо
    -> мост
    -> неизменяемый аудит в РУМЕКС
```

Боевой снимок создаётся при `mark_er_confirmed()`, когда отгрузка переходит в
`tn_ready`.

### Тестовый реестр

Тестовый поток **не совпадает** с целевой последовательностью
«диспетчер → бухгалтер → новая Таксимо». Фактически он работает так:

```text
Тестовый диспетчер
    -> create_test_shipment()
    -> test_shipment + ревизия + событие в РУМЕКС
    -> сразу тестовый снимок в rumex_taksimo_test_outbox
    -> мост передаёт ожидаемую приёмку в новую Таксимо

Бухгалтер РУМЕКС
    -> проверка / возврат на исправление / назначение ТТН
    -> documents_ready
    -> мост формирует и отправляет четыре XLSX-копии ТТН
```

Тестовый снимок намеренно передаётся без номера ТТН и без подтверждения ЭР:

```json
{
  "contract_version": 2,
  "physical_owner": "taksimo_new",
  "ttn_number": "",
  "confirmation": null
}
```

Новая Таксимо принимает контракт версии `2` без этих данных. Поэтому тестовый
рейс может оказаться в новой Таксимо до проверки бухгалтером.

Если тестовая погрузка остаётся в `awaiting_accountant_review` более 10 минут,
фоновая задача РУМЕКС автоматически резервирует номер ТТН и переводит запись в
`documents_ready`. Это системный переход, а не ручное бухгалтерское одобрение.

### Мост и очереди

`fotonych-bot/rumex_taksimo_bridge.py` — единственная серверная граница
обмена бизнес-фактами между РУМЕКС и новой Таксимо.

- Мост обращается к локальному HTTP API `http://127.0.0.1:8765` по умолчанию.
- Использует Bearer-токен `TAKSIMO_NEW_INTEGRATION_TOKEN` и `Idempotency-Key`.
- Не использует browser-cookie, PIN сотрудников, MAX-сессии или старую Таксимо.
- Не подключает SQLite РУМЕКС к MySQL напрямую.
- Подтверждает исходящий физический факт новой Таксимо только после успешной
  записи результата в РУМЕКС.

| Таблица | БД | Направление | Содержимое |
| --- | --- | --- | --- |
| `rumex_taksimo_outbox` | РУМЕКС SQLite | РУМЕКС → новая Таксимо | Боевой подтверждённый снимок |
| `rumex_taksimo_test_outbox` | РУМЕКС SQLite | РУМЕКС → новая Таксимо | Тестовый снимок без ТТН и ЭР |
| `rumex_taksimo_test_document_outbox` | РУМЕКС SQLite | РУМЕКС → новая Таксимо | Четыре копии ТТН |
| `tn_integration_outbox` | новая Таксимо MySQL | новая Таксимо → РУМЕКС | Исходящие физические факты |
| `rumex_taksimo_physical_events` | РУМЕКС SQLite | Получатель | Неизменяемый журнал принятых фактов |

Копии ТТН для тестовой записи создаются и передаются только если одновременно:

1. запись имеет статус `documents_ready` или `documents_handed_to_driver`;
2. у неё есть номер ТТН;
3. первоначальный тестовый снимок уже успешно доставлен в новую Таксимо.

## Известные ограничения текущей реализации

Это не план и не целевое состояние, а ограничения, подтверждённые кодом.

1. **Тестовый рейс поступает в новую Таксимо до проверки бухгалтером.**
   Он создаётся диспетчером и сразу ставится в исходящую очередь.
2. **Исправленная тестовая ревизия не создаёт новый снимок для новой Таксимо.**
   У тестового снимка закреплена версия документа `1`; после возврата
   бухгалтером и повторной отправки диспетчером новый состав блоков автоматически
   не передаётся.
3. **Документы не обновляют карточку ожидаемой приёмки.** Четыре XLSX-копии ТТН
   прикладываются к уже созданной приёмке, но номер ТТН исходного тестового
   снимка остаётся пустым.
4. **Обратные физические факты тестового реестра не поддержаны полностью.**
   Приёмник РУМЕКС проверяет связь с боевыми `rumex_taksimo_snapshots`, а не с
   `rumex_taksimo_test_snapshots`; поэтому физические события тестовой отгрузки
   могут быть отклонены.
5. Интерфейс тестового диспетчера говорит, что кабинет не меняет Таксимо. Старую
   Таксимо он действительно не меняет, но исходящее задание для новой Таксимо
   код всё же создаёт.

## Совместимость с legacy Таксимо

Новая Таксимо не пишет в legacy SQLite. Разрешённый способ чтения:

```text
SQLite URI mode=ro
короткое подключение
timeout = 2 секунды
одна read-транзакция для полного снимка
```

Разрешённые проекции legacy-снимка:

```text
vehicles
wagons
slots
slabs
yard_slabs
sessions
dispatch_slabs
wagon_history
```

Необязательная переменная `TAKSIMO_LEGACY_CUTOVER_AT` задаёт дату перехода в
ISO 8601 с часовым поясом.

| Условие | Режим |
| --- | --- |
| Дата X не задана | `live`: read-only просмотр SQLite |
| До даты X | `live`: согласованный read-only снимок для ответа |
| После X, архив есть | Неизменяемый MySQL-архив |
| После X, архива нет | Первый успешный запрос создаёт единый JSON-снимок в MySQL |
| SQLite недоступна после X | `snapshot_pending`; пустой архив не создаётся |
| Формат даты неверен | `configuration_error`; SQLite не читается |

Критичное ограничение: снимок создаётся при первом успешном запросе после даты
X, а не планировщиком в точный момент X. Дата перехода не зафиксирована
репозиторием.

## Авторизация

Авторизация контуров независима.

| Контур | Вход и cookie |
| --- | --- |
| Старая Таксимо | PIN из `TAKSIMO_USERS`, подписанный cookie `taksimo_auth` |
| Новая Таксимо | PIN операторов, серверная сессия `taksimo_new_auth` |
| РУМЕКС: бухгалтеры | PIN, серверная сессия `rumex_accountant_auth` |
| РУМЕКС: тестовый диспетчер | Пароль, серверная сессия `rumex_test_dispatcher_auth` |
| РУМЕКС: управление | MAX или пароль, серверная сессия `rumex_management_auth` |

Серверные сессии новой Таксимо и РУМЕКС хранят хэши токенов. Старая Таксимо
использует отдельный подписанный HMAC-токен в cookie. Cookie защищены
`HttpOnly` и `Secure`; значение `SameSite` зависит от контура: `Lax` у legacy
Таксимо и РУМЕКС, `Strict` у новой Таксимо.

Закрытые настройки новой Таксимо предполагаются вне репозитория в
`/root/.config/taksimo-new/`: отдельно для приложения, мигратора и резервного
копирования. Их содержимое не читается без разрешения.

## Миграции и эксплуатация

Миграции новой Таксимо находятся в `migrations/taksimo_new/` и запускаются
отдельным техническим пользователем через:

```text
scripts/migrate-taksimo-new-mysql.sh
```

Приложение не выполняет миграции самостоятельно.

| Группа | Содержание |
| --- | --- |
| `001` | Начальная схема MySQL-контура |
| `002` | Ограничения целостности и триггеры |
| `003–004` | Отмена операций и триггеры |
| `005–006` | Мост РУМЕКС и жизненный цикл физических фактов |
| `007` | Возврат порожнего вагона: схема и триггеры |
| `008` | Документы приёмки и копии ТТН |
| `009` | Legacy-архив и позиции вагонов 3 × 10 |

В каталоге есть две SQL-миграции с номером `007`: отдельные файлы для схемы и
триггеров. `009_legacy_archive_and_wagon_positions.sql` не изменяет SQLite;
фактическое применение этой миграции на production не подтверждено.

Скрипты резервного копирования и контроля:

- `scripts/backup-taksimo-db.sh` — backup legacy SQLite;
- `scripts/backup-rumex-registry-db.sh` — backup реестра РУМЕКС;
- `scripts/backup-taksimo-new-mysql.sh` — `mysqldump --single-transaction`,
  проверка `gzip`, SHA-256 и локальная ротация;
- `scripts/backup-env.sh` — резервная копия окружения;
- `scripts/taksimo-watchdog.sh` — проверка legacy API и перезапуск `bot.py` с
  cooldown.

Наличие скриптов не подтверждает расписание, успешность копий, возможность
восстановления или выгрузку в Object Storage. Watchdog не контролирует MySQL
новой Таксимо и мост РУМЕКС.

## Локальная разработка и проверка

Зависимости Python перечислены в `fotonych-bot/requirements.txt`: `maxapi`,
`openai`, `python-dotenv`, `aiohttp`, `openpyxl`, `PyMySQL`.

Для изменений новой границы legacy/новой Таксимо применялась следующая целевая
проверка:

```bash
python3 -m py_compile \
  fotonych-bot/taksimo_legacy_reader.py \
  fotonych-bot/taksimo_legacy_archive.py \
  fotonych-bot/taksimo_new_store.py \
  fotonych-bot/taksimo_new_api.py
node --check web/taksimo-new/app.js
git diff --check
python3 -m unittest \
  tests.test_taksimo_legacy_reader \
  tests.test_taksimo_legacy_archive \
  tests.test_taksimo_new_store \
  tests.test_taksimo_new_api
```

Исторический результат этой проверки: 24 теста прошли, 6 были пропущены из-за
отсутствующего `aiohttp`. Это не заменяет новую проверку после изменений и не
подтверждает production-состояние.

Перед коммитом:

1. Выполнить `git diff --check`.
2. Выполнить узкий `py_compile`, `node --check` и тесты затронутого контура.
3. Проверить `git status`.
4. Добавлять в индекс только явные целевые пути: `git add <пути>`.

## Правило для AI-разработчика

Перед задачей определить контур-владельца данных, прочитать его код и тесты,
а перед изменением межконтурного контракта найти все его использования. При
сомнении:

- legacy Таксимо не изменять; допускается только read-only доступ;
- границу РУМЕКС ↔ новая Таксимо пересекать только через мост;
- физические факты вести в MySQL `taksimo_new`;
- ТТН и ЭР вести в `rumex_registry.db`;
- production-операции, миграции и рестарты не выполнять без явного разрешения.
