# Утверждённый контракт

`POST /api/v1/dispatcher/trips`

**Статус: утверждён владельцем 13.10.2026 — `1A, 2A, 3A, 4A, 5A`.
Миграции `014–016` подтверждённо применены на целевой MySQL; исходный код
публикует endpoint через `create_app()` и по умолчанию использует
`AsyncMyTripRepository`.** Это не является deployment: в live Nginx по-прежнему
направляет API на legacy `bot.py` на порту `8765`, FastAPI-процесс не запущен,
поэтому внешний `POST /api/v1/dispatcher/trips` до отдельного deployment
возвращает ожидаемый `404`.

### Обязательные оговорки реализации

1. `create_app()` регистрирует маршрут и по умолчанию создаёт
   `AsyncMyTripRepository`. Приложение не применяет миграции автоматически;
   подключение MySQL в репозиториях ленивое. Миграция `014` только готовит
   канонические роли и права; устойчивая идемпотентность появляется в миграции
   `016`.
2. Для `POST /api/v1/dispatcher/trips` обязателен точный заголовок
   `Origin: https://avtmsk.ru`. Отсутствующий или иной `Origin` получает `403`
   до проверки сессии, прав и обращения к MySQL.
3. `GET /api/v1/healthz` подтверждает liveness процесса без MySQL.
   `GET /api/v1/readyz` проверяет обязательную конфигурацию и read-only доступ
   к MySQL; при неполной конфигурации или недоступности хранилища возвращает
   безопасный `503`.
4. Развёртывание FastAPI, отдельный MySQL-пользователь, порт, Nginx и
   production E2E остаются отдельными согласуемыми действиями.

## 1. Границы и обозначения

* **ПОДТВЕРЖДЁННЫЙ ФАКТ** означает, что утверждение непосредственно следует из
  указанного локального файла и строк. Состояние конкретной MySQL-инсталляции
  подтверждается только отдельной эксплуатационной проверкой.
* **УТВЕРЖДЁННОЕ ПРОЕКТНОЕ РЕШЕНИЕ** — согласованное правило нового
  FastAPI-контура. Оно не выдаётся за уже реализованное поведение миграции или
  legacy-кода. Все пункты **P1--P11** ниже утверждены владельцем 13.10.2026.

### Следствия из фактов

1. Точный JSON нового FastAPI-маршрута не задан ни миграциями, ни README:
   `CreateTrip` и `TripResponse` в README — только имена в примере.
2. Legacy-контур — исследовательский источник правил, но не контракт нового
   API: он допускает неполные снимки справочников и разрывает создание рейса и
   регистрацию паспорта на две транзакции.
3. Существующий `tn_integration_inbox` нельзя переиспользовать для HTTP
   идемпотентности рейса: его единственная предметная ссылка — `intake_id`.

## 3. Утверждённый минимальный HTTP-контракт

Все пункты данного раздела — **утверждённые проектные решения P1--P8**, если
явно не сказано «подтверждённый факт». Они составляют один согласованный
контракт.

### 3.1. Маршрут, доступ и заголовки

```text
POST /api/v1/dispatcher/trips
Origin: https://avtmsk.ru
Content-Type: application/json
Idempotency-Key: <UUID>
```

* **Защита источника.** До аутентификации router-level dependency требует
  точный `Origin: https://avtmsk.ru`. Отсутствующий или иной источник получает
  `403 {"detail": "Источник запроса не разрешён"}` без проверки сессии,
  прав или создания фактов.

* **P1. Capability и роль.** Маршрут использует
  `require_permission("trip.create", "edit")`. После подтверждения `016`
  dependency читает роль, базовый grant и nullable override учётки из
  `tn_roles`, `tn_role_permissions` и `tn_account_permissions`; override
  имеет приоритет над правом роли. Поэтому устаревший код роли сессии не может
  обойти точечный запрет или grant.

  Обоснование: это следует целевой модели доступа; проверка остаётся серверной
  dependency, а не условием в обработчике или на фронтенде.

* **P2. Заголовок идемпотентности.** `Idempotency-Key` обязателен, содержит
  канонический UUID и относится к одной семантической команде создания рейса.
  Ключ нельзя использовать повторно с другим нормализованным телом запроса.

  Обоснование: правило заголовка прямо задано README; UUID не несёт
  персональных данных и удобно проверяется на HTTP-границе. Применённая `016`
  долговечно хранит ключ, отпечаток команды и успешный ответ в отдельной
  таблице; fake-репозитории по-прежнему используются только в тестах, без
  подключения к MySQL.

* **P3. Закрытое тело.** Неизвестные поля в корне и в `blocks[]` отклоняются.
  JSON должен быть объектом; `Content-Type` — `application/json`.

  Обоснование: это не даёт клиенту молча рассчитывать на непроверяемые поля и
  удерживает минимальный контракт от случайного расширения.

### 3.2. Точное тело запроса

```json
{
  "trip_date": "2026-10-13",
  "vehicle_id": 42,
  "carrier_id": 7,
  "driver_id": 19,
  "blocks": [
    {
      "letter": "A",
      "number": "901",
      "suffix": ""
    }
  ]
}
```

| Поле | Тип и правило | Статус решения |
| --- | --- | --- |
| `trip_date` | Обязательная строка ISO `YYYY-MM-DD`. Время и часовой пояс не принимаются. | **P4.** В `tn_trips.trip_date` хранится обязательный `DATE`; явная дата делает повтор команды детерминированным. Ограничение «не в будущем» не вводится: его нет в подтверждённых источниках. |
| `vehicle_id` | Обязательное положительное целое. Должно обозначать существующую активную запись `tn_vehicles`. | **P4.** Сервер получает `plate` из справочника и фиксирует снимок; это не допускает произвольный номер машины в документном факте. |
| `carrier_id` | Обязательное положительное целое. Должно обозначать существующую активную запись `tn_carriers`. | **P4.** Сервер фиксирует снимок юридических данных перевозчика. Автоподстановка из машины, допускаемая legacy-кодом, не переносится без явного решения. |
| `driver_id` | Обязательное положительное целое. Должно обозначать существующую активную запись `tn_drivers`. | **P4.** Сервер фиксирует снимок ФИО и номера удостоверения. Это исключает создание черновика, который уже не содержит данных для последующей ТТН. |
| `blocks` | Обязательный массив от 1 до 16 элементов. | **P5.** Нижняя граница соответствует legacy-созданию; верхняя — единственному ограничению `tn_trips.block_count`. Правило печати ТТН «от 3 до 6» не применяется к созданию рейса: legacy-тесты относятся к печати, а не к вставке рейса. |
| `blocks[].letter` | Обязательная строка ровно из одной буквы `A`, `B`, `C`, `D`, `E`, `F` или `K`; сервер приводит к верхнему регистру перед проверкой. | **P6.** Допустимый набор подтверждён миграциями и legacy. |
| `blocks[].number` | Обязательная непустая строка длиной от 1 до 40 символов. | **P6.** Верхняя граница соответствует `tn_trip_blocks.block_number`. Для проверки повтора и ключа паспорта сервер нормализует номер: убирает все пробельные символы и приводит к верхнему регистру. |
| `blocks[].suffix` | Необязательная строка; при отсутствии — `""`; длина не более 8 символов. Значение должно быть одним из `""`, `"к"`, `"а"`, `"тк"`, `"скол"`. | **P6.** Допустимые значения подтверждены справочником суффиксов; `suffix_code` хранится в снимке строки и паспорте. |

**P6. Дополнительные правила блоков.** После нормализации в одном запросе не
должны повторяться `letter + number`; например, `A / "90 1"` и `a / "901"`
конфликтуют. Сервер берёт `weight_kg` и `price_rub` только из
`tn_block_types` по букве и сохраняет их как снимки. Поля `weight_kg` и
`price_rub` клиент не передаёт.

Обоснование: веса и цены по умолчанию подтверждены справочником, а снимки —
схемой строк рейса. Исключение пользовательских переопределений не вводит
неутверждённую финансовую логику.

**P7. Правило уже известного паспорта.** Если канонический `block_key` уже
есть в `tn_block_registry`, весь запрос завершается `409` и не меняет данные.
Новый маршрут не повторяет legacy-поведение «найти или создать».

Обоснование: `block_key` уникален и паспорт несёт сквозное состояние и
историю. Явный конфликт безопаснее, чем неявно прикрепить физический блок с
прошлой историей к новому рейсу. Это утверждённое намеренное отличие от legacy: миграция не запрещает повторное
использование сама по себе.

### 3.3. Успешный ответ

**P8.** Новый рейс отвечает `201 Created` следующим телом. В URL следующих
операций используется `trip.public_id` как публичный идентификатор; внутренние
числовые ключи рейса, строк и паспорта не возвращаются.

```json
{
  "trip": {
    "public_id": "08f1b37d-a5a3-4d32-8ee2-4ccd31a0231f",
    "status": "draft",
    "trip_date": "2026-10-13",
    "vehicle": {
      "id": 42,
      "plate": "А123ВС75"
    },
    "carrier": {
      "id": 7,
      "legal_form": "ООО",
      "name": "Перевозчик",
      "inn": "1234567890"
    },
    "driver": {
      "id": 19,
      "full_name": "Иванов Иван Иванович",
      "license_number": "75 АА 123456"
    },
    "block_count": 1,
    "total_weight_kg": 7780,
    "blocks": [
      {
        "letter": "A",
        "number": "901",
        "suffix": "",
        "weight_kg": 7780,
        "price_rub": "0.00"
      }
    ],
    "created_at": "2026-10-13T19:27:08Z"
  }
}
```

Обоснование: все данные ответа — публичный ключ либо снимки, которые уже
сохраняются в `tn_trips` и `tn_trip_blocks`; стоимость представлена строкой с
двумя знаками, чтобы JSON не превращал денежное значение `DECIMAL(12,2)` в
неточный `float`. Идентификаторы справочников возвращаются, потому что они
были явной частью команды; внутренние ключи нового рейса и блоков не нужны
клиенту. Время передаётся в UTC с суффиксом `Z`.

## 4. Статусы и безопасные ошибки

Форма проектной ошибки для отказов, которыми владеет новый маршрут.
Существующая auth dependency до отдельной общей унификации сохраняет
подтверждённые ответы `{"detail": "Требуется вход"}` (`401`),
`{"detail": "Недостаточно прав"}` (`403`) и
`{"detail": "Сервис авторизации недоступен"}` (`503`).

```json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте поля запроса",
    "fields": [
      {"field": "blocks[0].letter", "code": "invalid_value"}
    ]
  }
}
```

| HTTP | Код ошибки | Когда | Утверждённое решение |
| --- | --- | --- | --- |
| `201` | — | Новый рейс атомарно создан. | **P8** |
| `200` | — | Повтор с тем же `Idempotency-Key` и тем же нормализованным телом. Тело в точности равно сохранённому успешному ответу. | **P2** |
| `400` | `invalid_json`, `invalid_idempotency_key` | Тело не JSON-объект или заголовок отсутствует/не UUID. | **P2, P3** |
| `401` | — | Нет действующей серверной сессии; точное тело: `{"detail": "Требуется вход"}`. | Подтверждено текущей dependency. |
| `403` | — | Отсутствующий или иной `Origin` даёт `{"detail": "Источник запроса не разрешён"}` до аутентификации. При правильном источнике сессия без `trip.create` / `edit` получает `{"detail": "Недостаточно прав"}`. | Подтверждено router-level и permission dependency. |
| `404` | `vehicle_not_found`, `carrier_not_found`, `driver_not_found` | Указанный справочник отсутствует или неактивен. | **P4** |
| `409` | `block_already_registered`, `idempotency_key_reused` | Уже существует паспорт канонического блока; либо ключ повтора пришёл с другим нормализованным телом. | **P2, P7** |
| `415` | `unsupported_media_type` | `Content-Type` не `application/json`. | **P3** |
| `422` | `validation_error` | JSON имеет неверную форму/типы, нарушает ограничения полей, содержит неизвестное поле, повторяет блок в массиве или не находит тип блока в `tn_block_types`. | **P3--P6** |
| `503` | `storage_unavailable` | Нельзя завершить транзакцию из-за временной недоступности хранилища. | **P9.** Для auth-недоступности dependency уже возвращает `{"detail": "Сервис авторизации недоступен"}`. |

**P9.** Ответ не включает SQL, стек, имя таблицы, имя драйвера, cookie, токен
или детали другого пользователя. Для `422` допускаются только имя поля и
стабильный машинный код; исходное значение поля не отражается.

## 5. Утверждённая граница транзакции и компенсация

**P10. Одна транзакция создания.** После проверки сессии, capability и
структуры JSON одна короткая транзакция должна:

1. проверить существование и `active` выбранных машины, перевозчика и водителя;
2. загрузить типы блоков, проверить уникальность новых канонических ключей и
   отсутствие этих ключей в `tn_block_registry` с блокировкой записи;
3. создать `tn_trips` в статусе `draft`, строки `tn_trip_blocks` со снимками
   веса и цены, новые `tn_block_registry` и связи
   `tn_trip_blocks.registry_block_id`;
4. записать по одному `trip_declared` в `tn_block_history` и установить новым
   паспортам состояние `in_transit`;
5. записать действие создания в `tn_action_log` и устойчивый результат
   идемпотентности;
6. зафиксировать транзакцию и только после этого вернуть `201`.

Если любой шаг до `COMMIT` завершился ошибкой, откатываются все перечисленные
изменения, в том числе запись ключа повтора. В HTTP-обработчике нет внешнего
вызова, генерации ТТН или отправки уведомления; поэтому компенсирующая
операция не нужна и не должна маскировать частично созданный факт.

Обоснование: миграции подтверждают все предметные записи пунктов 3--5, а
README требует одну транзакцию для изменения бизнес-факта. Объединение двух
последовательных legacy-транзакций — **P10**, выбранное именно для устранения
окна, в котором рейс создан, но паспорт/история блока отсутствуют. Создание
рейса не включено в подтверждённый список MAX-событий, поэтому outbox для него
не создаётся без отдельного решения.

### Идемпотентность при сбое сети

**P11.** Устойчиво сохраняются: `Idempotency-Key`, отпечаток нормализованной
команды, HTTP-статус и успешное тело ответа. Повтор того же ключа и отпечатка
после потерянного ответа возвращает сохранённый `200` без новых фактов.
Повтор с другим отпечатком возвращает `409`; ключи не имеют общего пространства
между различными маршрутами и аутентифицированными учётными записями.

Это поведение нельзя реализовать через `tn_trips`, `tn_integration_inbox`
или outbox: у рейса нет поля ключа, а integration inbox семантически и ссылочно
принадлежит приёмкам. После подтверждённого применения `016` runtime использует
`tn_command_idempotency` с областью `(actor_account_id, operation_code,
idempotency_key)`. Для этой команды фиксированы `operation_code`
`dispatcher.trip.create`, алгоритм `sha256` и версия канонизации
`normalized-json-v1`: SHA-256 компактного JSON нормализованной Pydantic-команды
с сортировкой ключей. Эти значения сохраняются вместе с отпечатком и не
меняются при replay.

## 6. Что не включено намеренно

* Выдача номера ТТН, создание четырёх копий, передача бухгалтеру, передача
  водителю и выезд — отдельные маршруты из плана диспетчера
  ([`README.md:545-553`](../README.md)).
* Клиент не передаёт статус, `public_id`, значения снимка или автора: сервер
  получает их из команды, справочников и текущей сессии.
* Нет создания/редактирования справочников, подстановки по номеру машины,
  пользовательского переопределения веса/цены и частично заполненного черновика.
  Это возможные расширения, но ни одно не требуется для безопасного минимума.
* Runtime не применяет миграции. `GET /api/v1/readyz` выполняет только
  read-only проверку MySQL, а `GET /api/v1/healthz` не обращается к MySQL.
  Маршрут создания рейса подключён в `create_app()`, но live deployment ещё
  не выполнен.

## Утверждённые решения

Владелец утвердил `1A, 2A, 3A, 4A, 5A` 13.10.2026:

1. **1A — контракт полей (P3--P6).** Обязательны `trip_date`, `vehicle_id`,
   `carrier_id`, `driver_id` и от 1 до 16 блоков; вес и цена берутся сервером
   как снимки из справочника. Неполный черновик и legacy-автоподстановки не
   входят в контракт.
2. **2A — повторный паспорт блока (P7).** Уже существующий канонический
   `block_key` завершает весь запрос `409`; legacy-подход «найти или создать»
   не используется.
3. **3A — идемпотентность (P2, P11).** Канонический UUID в
   `Idempotency-Key` обязателен. Первое создание возвращает `201`, повтор с тем
   же нормализованным телом — сохраненный ответ с `200`, другой запрос с тем же
   ключом — `409`. Устойчивое хранилище предоставляет подтверждённо применённая
   миграция `016`.
4. **4A — атомарность (P10).** Рейс, строки, паспорта, история, аудит и запись
   идемпотентности создаются одной транзакцией без внешних побочных эффектов.
5. **5A — публичный ответ и ошибки (P8--P9).** Ответ содержит
   `trip.public_id`, серверные снимки и цену десятичной строкой; применяются
   статусы и безопасные конверты ошибок из раздела 4.

`create_app()` публикует endpoint с `AsyncMyTripRepository`; исходный код
покрыт изолированными fake- и SQL-репозиторными тестами. Это не меняет live
контур: до отдельного deployment FastAPI не запущен, Nginx и legacy `bot.py` на
порту `8765` не изменяются, а production-записи не создаются.
